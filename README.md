# IO Recorder

WindowsアプリのファイルI/OをETWで記録し、元ファイルを持ち出さずに、乱数ダミーファイルでストレージ負荷を再生するツールです。After Effects等の制作アプリから、ローカルSSD・NAS・LucidLinkへの移行を調べる用途を想定しています。

## 起動

`Start IORecorder.cmd` または `dist\IORecorder-win-x64\IORecorder.exe` をダブルクリックします。配布フォルダには.NETランタイムを含むので、利用するPCにSDKやVisual Studioをインストールする必要はありません。Windows 11 x64向けです。

GUIはETW計測のため**常に管理者として起動**します（起動のたびにWindowsのUAC確認が出ます。承認は利用者が操作してください）。常駐サービス・独自ドライバー・対象アプリへのDLL注入は使用しません。CLIは `record` だけが管理者権限を必要とし、`generate` / `replay` / `bench` などは通常権限で動きます。

管理者として動くプロセスからは、通常権限でつないだネットワークドライブ（`net use`）などが見えないことがあります。LucidLinkなどのドライブを試験先や計測対象にする場合は、最初に一度、管理者のPowerShellで `Get-ChildItem L:\` のように中身が見えることを確認してください。見えない場合は、UNCパスで指定するか、CLIの `resolve-root`（通常権限）と `record --root-device` を使います。

## 保存場所

ツールが書き込むものは、すべて `ドキュメント\IORecorder\` の下に置きます（場所は固定です。左下の「フォルダを開く」で開けます）。

```text
ドキュメント\IORecorder\
├─ settings.json   画面の入力の前回値
├─ Recordings\     ライブ計測の記録（その記録を再生した結果も同じフォルダ）
├─ Benchmarks\     ベンチマークのレポート
├─ Configs\        ベンチマークの構成ファイル（初回起動時に同梱のサンプルをコピー）
├─ Verification\   Verify ETW の結果
├─ Demo\           CLI の demo コマンドの合成データ（開発用）
└─ Temp\           再生時の並べ替えに使う一時ファイル（終わると削除）
```

フォルダ名は `日時_内容` の形です（例: `Recordings\20261017-153012_AfterFX`、`Benchmarks\20261017-153012_benchmark-anime_seed42`）。空白や使えない文字は `-` に置き換えます。

例外はダミーファイルだけです。測る対象のストレージに置く必要があるため、画面で選んだ**試験先フォルダ**の下に、同じく `日時_内容` のフォルダを作って置きます。

## 権限とセキュリティ

IO Recorderは、WindowsのETW（カーネルのイベントトレース）でファイルI/Oを記録するため、管理者権限で動きます。何のためにどの権限を使うかを、ここにまとめます。

| 使うもの | 目的 |
|---|---|
| 管理者権限 | ETWのカーネル計測（ファイルI/O・プロセス・物理ディスクI/O・メモリマップ）を始めるため。GUIは常に管理者で起動し、CLIは `record` だけが必要とします |
| デバッグ特権（`SeDebugPrivilege`） | 記録の開始時に、すでに開いているファイルを調べるため。対象のプロセスのファイルハンドルを複製してファイル名を読み、すぐ閉じます（ファイルの中身は読みません）。CLIでは `--no-open-files` で使わないようにできます |
| プロファイル特権（`SeProfileSingleProcessPrivilege`） | メモリのうちファイルキャッシュとして残っている量（Standby）と、まだ書き出していない量（Modified）を読むため |
| 外部プログラム | 記録の開始時に `fltmc filters`（フィルタードライバーの一覧を表示するだけ）を実行します。LucidLinkのCLIは、設定したときだけ統計の表示（`lucid perf`）に使います |

- **通信しません。** 記録した内容をどこにも送りません。保存先はこのPCの `ドキュメント\IORecorder\` と、ダミーを置く試験先フォルダだけです。ネットワークアダプターの送受信量は、OSの統計値を読むだけです。
- **入れないもの:** 常駐サービス、ドライバー、ほかのアプリへのDLLの注入、自動更新はありません。
- **記録に入る情報:** ファイルの中身は記録しません。ファイルのパス、プロセス名とコマンドライン、PC名、ネットワークアダプターの名前などは入るので、記録を人に渡す前に確認してください。
- **ウイルス対策ソフト:** カーネルの計測とハンドルの複製を使うため、誤検知される可能性があります。リリースのzipは、SHA-256と、GitHub Actionsでこのリポジトリのコードからビルドされたことの証明（公開リポジトリのとき）で確かめられます（[SECURITY.md](SECURITY.md)）。

脆弱性の報告方法は [SECURITY.md](SECURITY.md) にあります。

## ライブ計測

何を記録するかは、**計測対象のアプリケーション**と**対象フォルダ**で決めます。どちらか一方だけでも、両方でも指定できます。

- アプリだけ: そのアプリのI/O（どこへのものでも）
- フォルダだけ: そのフォルダへのI/O（どのプログラムのものでも）
- 両方: そのどちらか（OR）。アプリがローカルのキャッシュに書く分も、ほかのプログラムが対象フォルダに触れた分も入ります。「アプリのI/Oのうち、フォルダの中だけ」は、記録した後に02の「場所で絞り込む」で見られます

**手順（制作現場の担当者に頼むときもこの形）**:

1. 測るアプリを閉じた状態で、IO Recorderを起動します。
2. 「アプリを選ぶ…」を押すと「計測対象のアプリケーションを選択」が開きます。
   - **インストール済みのアプリ**: スタートメニューのアプリ（「Adobe After Effects 2025」など）から選びます。
   - **実行中のプロセス**: いま動いているプログラムから選びます（ウィンドウのあるものが上）。選ぶのは1つのプロセスではなく、そのプログラムです（インストール済みから選んだのと同じ扱い）。いま動いているので、「計測を始めたら、このアプリを起動する」は外した状態にします（起動中のアプリをそのまま記録します。起動したときの読み込みも記録するときは、アプリを閉じてからチェックを付けます）。
   - どちらにもないアプリは「一覧にないアプリを選ぶ…」で、プログラム（`.exe`）かショートカットを選べます。
   - 選んだアプリは次から覚えています。やめるときは、選んだ後のボタン「キャンセル」を押します。
3. 必要なら対象フォルダを指定します（1行に1つ。`L:\Production`、`D:\素材`、UNC共有。記録の保存先は対象フォルダの外に置きます。ドライブ文字はNTデバイスパスとUNCにも解決して照合します）。
4. 「計測を開始してアプリを起動」を押します。記録を始めてからアプリを起動するので、起動したときの読み込み（前回のプロジェクトや素材の一覧など）も記録に入ります。アプリは管理者ではない、ふだんの権限で起動します（エクスプローラーと同じ権限。ネットワークドライブも、いつもどおり見えます）。アプリが自分で管理者の権限を求めるもの（CrystalDiskMarkなど）は、そのアプリのユーザーアカウント制御の確認が出ます。
5. 普段の作業を行います。約1秒ごとにRead/Write MiB/s・IOPS・P95/P99・アクセス量の多いファイル・使用可能RAMを更新します。ETWのバッファリングにより表示は1～数秒遅れます。記録開始から10秒たっても対象フォルダに一致するI/Oが1件もない場合は警告を出します（パス解決の失敗を疑ってください）。
6. 作業が終わったら「停止して保存」でJSONL・CSV・HTMLレポートを確定します（ウィンドウを閉じた場合も停止処理を行います）。送るときは「記録をzipで書き出す…」で保存先のフォルダを選びます。

試験ラベルは記録の見分け用の任意のメモです（HTMLレポートの見出しと「記録を開く」の概要に表示）。空欄なら、開始時に `2026/10/17 AfterFX試験` のように日付とアプリのプログラム名（なければフォルダ名）から自動で付けます。LucidLinkを使う場合は、任意で `lucid.exe` の場所を指定すると、記録中に `lucid perf --all --seconds 1` の出力も保存します。複数のインスタンスを動かしている場合だけ、`lucid list` で調べたIDを指定します（`lucid --id <ID> perf …` として渡します）。

**アプリのどのプロセスを記録するか**:

- 選んだアプリのプログラム（After Effectsなら `AfterFX.exe`。表示名ではなく、プログラムのファイル名で照らし合わせます）。作業の途中でアプリが落ちて、いつもの方法で起動し直しても、名前で記録を続けます。
- そのアプリが起動したプロセス（子・孫）。子プロセスかどうかは、そのプロセスが起動したときに決めて覚えておくので、親が先に終わっても記録は続きます（After Effectsを閉じた後のレンダリング用のプロセス、本体を起動してすぐ終わる起動用のプログラムなど）。親のプロセスIDが終了後に別のプログラムに使い回されていても、そのプログラムの子は対象になりません。
- 選んだアプリと同じフォルダ（とその下）にあるプログラム。誰が起動したかに関係なく対象にします（ランチャーがほかのプログラムに起動を頼むアプリ、ストアアプリ、After Effectsの `aerender.exe` など）。Windowsのフォルダ、Program Filesそのもの、ドライブの直下、デスクトップ・ダウンロード・ドキュメントに直接置かれたプログラムは、関係のないプログラムも同じ場所にあるので、この扱いをしません。
- アプリがもう起動していると、起動したときの読み込みは記録できないので、そのまま記録するか、アプリを閉じてやり直すかを確認します。

対象にしなかったプロセスのI/Oも、ファイル名は残さずに、プロセスとドライブごとの件数と量だけ数えて `session.json` に残します（`otherProcessIo`）。02の概要とHTMLレポートには、そのうち記録と同じドライブへのI/Oが多かったものを出します。アプリの仕事を、子でも同じフォルダでもない別のプログラムが行っていた場合に気づけるようにするためです。

画面で選べるアプリは1つです。複数のプログラム名やPIDを指定するときは、CLIの `record --process`（複数回指定可）・`--pid` を使います。

事前のフォルダウォークはしません。初めて観測したファイルだけを登録し、アプリのアクセスの後にそのファイルの大きさを照会します（中身は読みません）。ダミーを実物に近い大きさで作るためです。アプリが既にアクセスしたファイルのメタデータを読むだけなので試験への影響はごく小さいものの、照会の分だけLucidLinkの統計（Filespace全体の値）にメタデータ操作が加わります。GUIでは常に有効で、CLIでは `--no-size-probe` で無効にできます。

## 記録を見る

「記録を開く」から `session.json` を含むフォルダを選びます。記録全体の数値（平均・1秒あたりの最大・合計・P50/P95/P99）、時系列グラフ、ファイル別のアクセス量、パス・プロセス名・操作名によるイベント検索を使えます。全イベントのCSVが必要なときは「CSVを書き出す」を押します。画面が縦に収まらないときは、右側全体をスクロールします。

時系列グラフは、転送量（MiB/s）・IOPS・レイテンシP95の3段で、時間軸は共通です。青がRead、緑がWriteです。レイテンシは、その秒に始まった成功Read/WriteのP95で、対数目盛です（I/Oがない秒は線が切れ、前後にI/Oがない1秒だけの値は点で表示）。グラフにカーソルを重ねると、その秒の値を3段それぞれに表示します。ライブ計測中は直近2分を表示します。

1秒ごとのレイテンシを持たない古い形式の集計（`analysis.json`）は、記録を開いたときに一度だけ集計し直し、`analysis.json`・`timeline.csv`・HTMLレポートを書き換えます（大きな記録では数十秒かかります）。

**場所で絞り込む**: 概要の右の「場所で絞り込む…」で、記録がI/Oを出したフォルダの一覧（ドライブ・共有ごとの木と、それぞれの読み書きの量・操作の件数）から、場所を選べます。プロセスを指定した記録には、アプリのI/Oが置き場所に関係なく全部入る（素材のほかに、Cドライブのプラグイン・フォント・環境設定・キャッシュなど）ので、たとえば素材のフォルダだけに絞って見るときに使います。

- 選んだ場所は記録に保存し（`locations.json`）、02の集計とHTMLレポート、03のダミー生成と再生、05の比較のすべてに効きます。記録全体の集計（`analysis.json`・`report.html`）はそのまま残し、絞り込んだ集計は別に保存します（`analysis-locations.json`・`report-locations.html`）。絞り込みを変えると集計し直すので、大きな記録では時間がかかります。
- フォルダを選ぶと、その中のものすべてです。フォルダの中のフォルダを一部だけ選ぶと、そのフォルダの直下のファイルは入りません（入れるときは「（このフォルダの直下のファイル）」を選びます）。
- パスが分からないI/Oは、絞り込むと入りません。「CSVを書き出す」は、絞り込みに関係なく記録の全部です。
- 取り直しは要りません。これまでの記録にも使えます。

**zipで書き出す・取り込む**: 「記録をzipで書き出す…」（01、記録を止めた後）と「zipで書き出す…」（02）は、記録のフォルダを1つのzipにまとめて、選んだフォルダに `記録のフォルダ名.zip` として保存します（同じ名前があれば `(2)` を付けます。書き終えるまでは `.part` の名前で書くので、途中で止まっても完成したように見えるzipは残りません）。集計やレポートなど、記録から作り直せるものは入れず、すでに圧縮したイベントの記録は圧縮し直しません。受け取った側は、02の「zipから取り込む…」でzipを選ぶと、保存先の `Recordings` に展開して開きます（zipの中に展開先の外を指すファイルがあれば、何も残さずに止めます）。ツールが管理者で動いているので、保存先を選ぶ画面にネットワークドライブが出ないことがあります。そのときはデスクトップなどに保存してから送ってください。

02の各項目（数値カード、時間ごとの推移、ファイルごとの読み方・分割単位の試算の各列）と03の再生の結果には「?」があり、マウスを重ねる・Tabキーで移動する・クリックすると説明が出ます。

**ファイルごとの読み方**（02の下の方とHTMLレポート）: アプリの要求（ページングI/Oを除く）から、ファイルごとに「どこを、どの大きさで、どの順に」読んだかを出します。

| 項目 | 意味 |
|---|---|
| 読み取り量 | 読み取った量の合計。読み取り量 = 再読み取り量 + 読み取り範囲 |
| 再読み取り量 | すでに一度読んだ場所をもう一度読んだ分（量と、読み取り量に対する割合）。キャッシュに残っていればキャッシュから返っているかもしれない量。HTMLではセルにカーソルを重ねると平均何回読んだかが出る |
| 読み取り範囲 / サイズ | 読み取られた部分の大きさ（重複を除く）とファイルサイズ。括弧はカバー率（読み取り範囲 ÷ サイズ）で、大きなファイルを一部だけ読むと低くなる。画面ではカバー率で並べ替わる |
| 読み取りサイズ | 1回の読み取り（システムコール）の大きさの中央値（HTMLはP95も）。2のべき乗の区切りの上限値 |
| 連続 | 同じハンドルの前の読み込みの続きから、または1 MiB以内の前方への読み飛ばしで読んだ割合 |
| 型 | 連続70%以上なら「全体を順に」（カバー率90%以上）か「一部を順に」、30%未満なら「散らばる（疎）」、その間は「混在」、3回以下は「数回だけ」 |

ファイルサイズはアクセスの後に照会した値か、読み書きした最も後ろの位置です。記録中に大きくなったファイルでは、カバー率がずれます。メモリに割り当てて読む方式（mmap）のファイルは、ページングI/Oとしてだけ記録されるので、この一覧には出ません。

**ファイルごとの書き方**（02とHTMLレポート）: 書き込みも同じ考え方でまとめます。書き込み量 = 再書き込み量 + 既存の上書き + 新しい部分で、書いたバイトは必ずこの3つのどれかに入ります。再書き込み量は同じ場所を書き直した分（書き込みをいったんローカルに置いて後からアップロードするストレージでは、アップロード前にまとめられれば減り得る量）、既存の上書きは記録の開始時点で既にあったデータへの1回目の書き込み（開始時のサイズ（推定）と並べ、上書きした割合も出す）、新しい部分は末尾への追記や新規ファイルの中身です。型は「新規に順に書く」「新規（順不同）」「末尾に追記」「既存を順に上書き」「既存の一部を上書き」「混在」「数回だけ」です。

**分割単位ごとの取得量の試算**（02とHTMLレポート）: LucidLinkのように、ファイルを同じ大きさの断片（チャンク）に分けて保存し、読まれた位置を含む断片を取りに行くストレージを想定します。64 KiB・256 KiB・1 MiB・4 MiBの各単位で、記録の読み込みが取りに行く断片の数（取得回数。キャッシュが空のときのキャッシュミスの回数）と量、効率（読んだ範囲 ÷ 取得量。100%なら無駄なし）を出します。書き込みは、更新される断片の数（更新回数）、アップロード量の下限（記録全体で同じ断片を1回にまとめられた場合）と上限（書き込みのたびに触れた断片を送る場合）、効率（書き込み範囲 ÷ 下限）、一部書き換え（開始時にあったデータの断片で、書き込みが一部しか覆わないものの数。アップロードの前に残りの内容が必要）です。キャッシュが空・先読みなし・一度取った断片は取り直さない、という前提の下限値で、実際の転送量や待ち時間の予測ではありません。分割単位の候補を比べる材料として使います。ファイルごとの値は記録フォルダの `access-patterns.csv` にあります。

「HTMLレポート」で標準ブラウザにレポートを開きます。転送量・IOPS・レイテンシの時系列グラフ、Read位置のヒートマップ、ファイルごとの読み方、分割単位ごとの取得量の試算、要求サイズの分布、拡張子別の転送量、計測品質を表示します。HTMLは単一ファイルで外部通信や外部ライブラリを使いません。ヒートマップはRead量上位12ファイルを対象に、開始オフセット64分割・時間120分割で表示します。

## 記録の再生（ダミー生成とリプレイ）

1. 記録を開いてから「記録の再生」を選びます。
2. **試験先フォルダ**（NAS・LucidLinkなど）と**再生する範囲**（記録した全I/O / 指定プロセスに一致 / 指定フォルダに一致）を指定して「ダミーファイルを生成」します。ダミーは、その範囲の再生が使うファイルだけ作ります（範囲を変えて再生するときは生成し直します。CLIは `generate` と `replay` に同じ `--process-only` / `--root-only` を付けます）。試験先の下に `日時_replay_記録フォルダ名` のフォルダを作り、元の `D:\Production\a.exr` をその中の `D\Production\a.exr` に変換して置きます。UNCパスも `UNC\server\share\...` に隔離します。02で場所を絞り込んでいれば、その中のI/Oが使うファイルだけでダミーを作り、再生もその中のI/Oだけを出します（ダミーに場所を残すので、再生はダミーの場所に従います。絞り込みを変えたら生成し直します）。素材をNASやLucidLinkに置いたときの評価では、素材のフォルダに絞ると、ローカルに置いたままのプラグインなどの読み込みを試験先で再生せずに済みます。
3. アクセスされた既存ファイルだけに、固定シードの疑似乱数を書き込みます。記録中に新規作成されたファイルは事前生成しません。ゼロ埋め・スパースファイルではなく、圧縮されにくいデータです。
4. LucidLinkで試験するなら、初期アップロードが完了してから、Cold / Warm / Pin等のキャッシュ条件を整えます。本ツールからキャッシュ消去やPin変更は行いません。
5. 再生タイミング・速度・最大並列数を設定して「リプレイを開始」します。
   - **ThinkTime**（既定。作業時間の比較向け）: 各スレッドで、前のI/Oが実際に終わってから、記録と同じ間隔（アプリの処理時間）を空けて次を出します。実際のアプリと同じく、試験先が遅ければ全体が伸び、速ければ縮みます。「このストレージだと作業がどれだけ長くなるか」を、再生にかかった時間と記録の長さで比べます。
   - **Timeline**（同じ負荷での遅延比較向け）: 記録の発行時刻どおりに出します。試験先の速さに関係なく記録と同じペースで負荷をかけ、遅れたスレッドは処理の間隔を飛ばして追いつこうとします。そのため遅い試験先では、実際のアプリより強い負荷になります。
   - どちらの方式でも、スレッド同士の待ち合わせ（別スレッドの完了を待つ等）は記録にないため再現しません。
   - 待ちは数十µsの精度で行います（専用スレッドで、高精度タイマーで眠ってから最後の約1 msを空回りして待つ。空回りに使うCPUは最大1コア）。
   - 再生クロックは、イベントの並べ替え（外部ソート）が終わり、最初のイベントを投入する時点で開始します。CLIの `--trim-leading-idle` で、記録開始から最初のI/Oまでの空白を詰められます。
6. 実行・失敗・スキップ件数と実測レイテンシを確認します。**投入の遅れ**（ThinkTimeは記録の間隔、Timelineは記録の時刻に対して、各I/Oを予定よりどれだけ遅く出したか。中央値・P95・最大）が小さければ、記録のペースどおりに再生できています。再生側の処理時間（1回あたり数十µs）より短い間隔は再現できず、その分が遅れとして出ます。詳細は元の記録フォルダの `replay-*.json` / `replay-*.jsonl` に保存します（`jsonl` の `plannedUs` は、ThinkTimeでは前のI/Oの完了時刻＋記録の間隔です）。

**再生中の記録と比較**（03と05）: 03の「再生中のI/Oも記録する」（既定オン。ETWを使うので管理者権限のときだけ）をオンにすると、再生の間、ダミーのフォルダへの全プロセスのI/Oを記録し、元の記録フォルダの `replays\日時_replay\` に普通の記録と同じ形式で保存します（再生したI/Oに加えて、OSのキャッシュ補充・遅延書き込みやウイルス対策の検査なども入ります。試験先への負荷を増やさないよう、ファイルサイズの照会はしません）。05「比較」では、開いている記録とその再生の記録を並べて、次のものを比べます。

- 数値: I/Oがあった時間（最初のアプリのRead・Writeの開始から最後の完了まで。µs単位で測る）、Read・Writeの合計・平均・最大、IOPS、レイテンシP50/P95/P99、Read・Write回数、ページングI/O、失敗した操作、高速I/Oの拒否（数えない）。差は「再生 − 元」と、元に対する増減の割合
- 時間ごとの推移: 元を実線、再生を点線で重ねる（どちらも最初のI/Oを0秒にそろえる）
- ファイルごとの比較: 読み取り量・書き込み量・レイテンシP95を「元 / 再生」で。ダミー側のパスは元のパスに読み替えて突き合わせる
- 操作の件数: 再生しなかった操作や、OSなどが追加で行った操作が分かる。Read・Writeは、アプリの要求と、OSが自分で行うキャッシュへの読み込み・書き戻し（ページングI/O）を分けて数える（ページングI/Oは、キャッシュにすでにデータがあるかで大きく変わる）
- プロセスごとの件数: 元と再生で、どのプロセスがI/Oを出したか。「（再生）」の付いた行が再生したプロセスで、元でどのプロセスが出した要求もこのプロセスがまとめて出す。それ以外の行の再生側は、再生中に試験先のOSやほかのプログラムが自分で出したI/O

元の記録を02で場所に絞り込んでいれば、両方ともその場所の中のI/Oだけで比べます（再生側は、ダミーのパスを元のパスに読み替えてから判定します。プロセスごとの件数にも効きます）。

「比べる範囲」（CLIは `--scope`）で、何を比べるかを選べます。どちらの範囲でも、数値は記録から計算したままで、合わせるための調整はしません。ダミーの管理ファイル（`.iorecorder-dataset.json` とその一時ファイル）はツール自身のものなので、どちらの範囲でも除きます。

- **全体**（既定、`all`）: 両方の記録を、記録されたまま（すべてのプロセス）比べる
- **再生した要求だけ**（`replayed`）: 元の記録のうち再生の対象にしたI/Oと、再生の記録のうち再生したプロセスが出したI/Oを比べる。再生中に試験先のOSやほかのプログラム（キャッシュの書き出し・ウイルス対策・検索インデックス）が出したI/Oは含まない。再生がどれだけ元どおりの要求を出せたかを見るときに使う

レイテンシはどちらもETWでファイルシステムに届いたI/Oを測るので、ストレージの違いをそのまま比べられます。再生の記録は02で普通の記録として開くこともできます。CLIは `replay --record`（管理者）と `compare --session <記録フォルダ> [--scope all|replayed]` です。

ツールの再生の精度そのものを確かめるときは、元の記録と再生を同じマシン・同じ種類のストレージで行い、デスクトップのような検索インデックスやウイルス対策の検査が多い場所は避けます（インデックス対象外のフォルダ、例えば `C:\IOTest` など）。試験先がユーザーのフォルダ（デスクトップ・ドキュメントなど。AppDataは除く）の中だと、ダミー生成と再生の結果に注意を出し、再生中に検索インデクサーが試験先を読んでいた場合は05「比較」にも注意を出します。実測では、デスクトップの再生は検索インデクサーのI/Oが毎回1万件以上混ざり、`C:\IOReplay` では0件でした。また、キャッシュの状態をそろえるため、どちらも再起動直後か、どちらも一度読み込んだ後に実行します。実際の試験先の評価では、こうしたOSやほかのプログラムの動きも現実の一部なので除きません。

ページングI/Oの再生方針（CLI `--paging`）は次のとおりです。再生側のOSも自分でキャッシュ補充やLazy Writeを行うので、記録したページングI/Oまで再生すると負荷が二重になります。

| 方針 | 内容 |
|---|---|
| `UnmatchedReads`（既定） | アプリ要求はすべて再生。ページングReadは、同じファイルの同じ1MiB領域に前後2秒以内のアプリReadがなければmmap由来とみなして通常のReadとして再生し、あればキャッシュ補充としてスキップ。ページングWriteは再生しない |
| `None` | ページングI/Oはすべて再生しない |
| `All` | すべて再生（旧来の挙動）。IoFlagsがない旧形式の記録はこの扱いになる |

再生はスレッド内と同じファイルオブジェクトの順序を維持し、最大並列数を制限します。実際の投入遅れも記録します。厳密なWindowsの非同期I/Oキュー・アプリのCPU/GPU処理を再現するものではありません。1回の要求は1回のRead/Writeとして発行し、64MiB超の要求はスキップを記録します。

ダミーのフォルダには本ツールの識別ファイル（`.iorecorder-dataset.json`。記録上のパスとダミー側のパスの対応表などを持つ）が必要で、別の記録から作ったダミーには再生しません。記録上のパスの表記の違い（末尾の `\`、大文字小文字、`\\?\`）は同じファイル・フォルダとしてまとめます。変換・作成できない名前（`..` や予約名を含む、試験先が受け付けない名前など）と、ダミーのフォルダの外を指すパス・中のリンク（ジャンクション・シンボリックリンク）を経由するパスは、生成・再生を止めずにそのパスだけ対象外にし、再生結果のスキップ件数（`SkippedUnresolvedPath` / `SkippedUnsafePath`）と注記に残します。リンクの先へは読み書きしません。試験先フォルダより上の階層がリンク（リダイレクトやマウント）でも使えます。再生するとダミーの中身が変わるので、再生後は「実行済み」として、そのままでは再生できない状態にします。同じ条件でもう一度再生するときは「**ダミーを初期状態に戻す**」を押します（CLIは `reset --target <ダミーのフォルダ>`）。実行で作られたファイルとフォルダを削除し、消えたファイルを作り直し、サイズを戻し、**書き換えられた範囲だけ**を元の内容で書き戻します（ダミーの中身はseedから途中の位置でも計算できるため）。全部を作り直すより速く、LucidLinkでも変わった部分だけのアップロードで済む見込みです（実機では未確認）。原本に対してリプレイしません。

## ベンチマーク（合成負荷）

記録がまだない段階や、条件を変えて同じ負荷を何度もかけたい場合に使います。構成ファイル（JSON、コメント可）に「どんなファイルを何個」「どんな読み書きをどの比率で」を書くと、それを**記録と同じ形式のI/O列**に展開し、ダミーファイルに対して実行します。

- **決定論的**: 同じ構成・同じ `seed` なら、対象ファイル・順序・オフセット・サイズ・書き込み内容まで毎回同じI/O列になります（`events.jsonl` がバイト単位で一致）。変わるのは、試験先のストレージが返す実測時間だけです。`seed` は数字（`42`）でも文字列（`LucidLink試験A`）でも指定できます。文字列は決まった計算で数値に変換するので、同じ文字列なら同じI/O列になります。空欄や記号だけの入力は「指定なし」として構成ファイルの値を使います。
- **ファイル群**（`fileSets`）: `count` 個のファイルを `size ± sizeJitter` で作ります。例: 1GiBを4個、8MiBを2400個。実際に使われるファイルだけがダミーとして生成されます。
- **負荷**（`workloads`）: `operation`（read / write）× `pattern` を組み合わせます。
  - `sequential`: ファイル内のランダムな位置から `runLength` 分を、`blockSize` ずつ連続で読み書き
  - `random`: ファイル内のランダムな位置（`blockSize` 単位）に、`runLength / blockSize` 回読み書き
  - `wholeFile`: readはファイル全体を先頭から読む（連番画像の読み込み）。writeは新しいファイルを作って書き切る（レンダリング出力）
- `weight` は**転送量の比率**です。各スレッドは、目標比率に対して最も不足している負荷を順に担当するので、シーケンシャルとランダムが全体に散らばります。1回のまとまり（例: 256MiBのシーケンシャル読み）が `totalTransfer` に対して大きいと、比率に誤差が出ます。
- `rateMiBps` が0なら全速です。各スレッドが前の要求の完了直後に次を発行します。値を指定するとその速度で一定に投入します。`replay` は構成に合った投入方式とスレッド数を自動で使います。
- 実行時間で決めるときは、`totalTransfer` の代わりに `duration`（例: `"30m"`、`"1h30m"`、`"90s"`、`"01:30:00"`）を書きます。`rateMiBps`（0より大きい値）と一緒に使い、合計量は `rateMiBps × duration` です（例: 50 MiB/s で30分 → 約88 GiB）。全速では試験先の速さで時間が変わるため、`duration` は使えません。試験先が指定の速度に追いつかないときは、その分だけ長くかかります。
- `totalTransfer` は、実際に使われるファイルの量とは別です。I/O列で使われたファイルだけをダミーとして作り、使われないファイルは作りません。`wholeFile` の `write`（レンダリング出力など）は実行のたびに新しいファイルとして残るので、「構成の概要」に「新規書き込み」として量を出します。生成の前と実行の前に、ダミーと新規書き込みの合計が試験先の空き容量に収まるかを確かめ、足りなければ何も書かずに止めます（ドライブ文字の試験先のみ。UNCは確認しません）。

**GUI**では「04 ベンチマーク」で、構成ファイル・レポートの保存先・試験先フォルダを選び、次の順に押します。

1. **ダミーファイルを生成**: 構成とseedからI/O列を作り、試験先に日時付きのフォルダを作ってダミーを置きます。レポートの保存先にも同じ名前のフォルダを作ります。
2. （LucidLinkなら、アップロードの完了を確認し、キャッシュ条件を整える）
3. **ベンチマークを実行**: 終わると負荷ごとの結果が表に出て、「レポートを開く」で結果のHTMLレポートを開けます。

実行中は、段階・進捗率・件数・直近のMiB/sを表示します。「構成を開いて編集」を押すと、同梱のサンプルをレポートの保存先にコピーしてからメモ帳で開くので、配布物のサンプルは変わりません。

**CLI**では次のとおりです。

```powershell
# 1. I/O列を作成（seedは --seed で上書きできる）。Benchmarks\日時_構成名_seed のフォルダができ、レポートもそこに保存
.\iorecorder-cli.exe bench --config "$env:USERPROFILE\Documents\IORecorder\Configs\benchmark-anime.json"
# 2. 試験先にダミーを生成 → LucidLinkならアップロード完了とキャッシュ条件を整える
.\iorecorder-cli.exe generate --session <1.で表示されたフォルダ> --target L:\Bench\<同じフォルダ名>
# 3. 実行。負荷ごとのMiB/s・IOPS・P50/P95/P99を表示し、HTMLレポート・JSON・1秒ごとのCSVを保存
.\iorecorder-cli.exe replay --session <1.で表示されたフォルダ> --target L:\Bench\<同じフォルダ名>
```

ダミーの生成と「初期状態に戻す」は、書いたデータをディスクまで書き終えてから完了します（OSのキャッシュに残ったまま再生を始めると、OSの書き出しと再生がディスクを取り合います。16 GBのダミーを作った約10秒後に始めた再生は、時間が約2倍になりました）。再生の前にも、OSがまだ書き出していないデータ（Modified）が減り続けている間は、最大60秒待ちます（管理者権限のとき。待った時間は再生結果に残ります）。

生成直後のダミーは、OSのキャッシュやLucidLinkのローカルキャッシュに載っています。このまま実行するとキャッシュ上の性能を測ることになるので、コールド条件で測るときはキャッシュを整えてから実行してください。同じ条件で繰り返すときは「ダミーを初期状態に戻す」を押してから実行します。戻した部分もキャッシュに載るので、コールド条件で測るときは改めてキャッシュを整えてください。

## 記録内容と精度

| 項目 | 実装 |
|---|---|
| Open / Read / Write / Cleanup / Close / Flush | ファイルオブジェクト・PID/TID・開始時刻を記録。IRPで完了と対応付け |
| Read / Writeの位置・要求サイズ | 64bitオフセット・要求バイト数を保存。完了から得た転送量は別フィールド |
| ページングI/O | IRPフラグ（`IoFlags`）を保存し、`IRP_PAGING_IO` / `IRP_SYNCHRONOUS_PAGING_IO` をページングとして区別。Read/Write・レイテンシ・要求サイズ分布・拡張子別量はアプリ要求（非ページング）のみで集計し、ページング量は別に表示 |
| 成否・遅延 | NTSTATUSと完了時刻。完了を取得できない操作は不明のまま保持。高速I/Oの拒否（`STATUS_FLT_DISALLOW_FAST_IO`。フィルタードライバーが高速な経路を断り、すぐ同じ要求がIRPで出し直されたもの）は1つの要求の重複なので、Read・Write回数や失敗には数えず、件数だけ別に出す |
| 明示的な伸長・切り詰め | SetInfoのFileEndOfFileInformationを記録し、再生時にEOFを設定 |
| Allocation Size | EOFと区別して記録・設定 |
| 新規作成 | 最初に成功したOpenの完了結果（`FILE_CREATED` か）で判定。それより前の「存在しない」失敗（存在確認）は、新規作成の根拠として扱う |
| ディレクトリ | `FILE_DIRECTORY_FILE`・ディレクトリ列挙・サイズ照会のいずれか、または他のパスの親であればディレクトリとして扱う（「パスが見つからない」で失敗したパスの親は除く。`a.psd\x` のようにファイルの下を探しただけでは、`a.psd` はフォルダにならない） |
| Rename | ETWのRenameは元のパスしか持たないため、同じFileKeyに後から現れた別の名前を宛先とする（最大2秒保留）。宛先が分かった場合のみ再生し、未解決はスキップ |
| Delete | 削除情報クラスが判明する場合にdelete-on-closeを近似。未判定はスキップ |
| QueryInfo / ディレクトリ列挙 | 要求を記録。再生では、記録と同じ情報クラス（列挙は同じバッファサイズ・検索パターン）で、元が使ったハンドルに対して1回ずつ出す。元の返却内容は記録されない。ダミーのフォルダには記録で触れたファイルしかないので、一覧は元より早く終わることがある |
| OSメモリ・CPU・通信量 | 1秒ごとに物理RAM・Available・Commit・System Cache・Standby（ファイルキャッシュとして残っている量）・Modified（まだ書き出していない量）・マシン全体のCPU使用率、対象プロセスのWorking Set・Private Bytes・CPU使用率、ネットワークアダプターごとの送受信の累計バイト数 |
| Hard Fault / 物理ディスクI/O | 論理ファイルI/Oと区別して保存・集計。物理ディスクI/Oはディスク番号とIRPフラグも残す。物理ディスクのオフセットをファイルのオフセットとして再生しない |
| ファイルの識別 | Open以外のイベントに `FileKey`（ファイルの実体。ハンドルや名前が違っても同じファイルなら同じ値）を残す |
| 記録開始前から開いていたファイル | ETWはファイルを開いたときに名前を知らせるので、開始前に開かれたファイルへのI/Oは名前が分からない。開始時に、開いているファイルの一覧（ハンドルとファイルオブジェクトの対応）をOSから取ってパスを補い、`open-files.jsonl` に残す。記録中も、同じファイル（`FileKey`）の名前が別のイベントで分かれば、それで補う。補えなかったI/Oはプロセスごとの件数を `session.json` の `unresolvedPathsByProcess` に、最初の2,000件の内容を `unresolved-sample.jsonl` に残す（ファイルのI/Oの要求だけを数える。メモリの割り当て・解除、ページフォールト、物理ディスクI/Oは、もともとファイルのパスを持たないので数えない。アプリだけを指定した記録では、対象のプロセスと、対象のファイルへのI/Oだけを数える。フォルダを指定した記録では、パスが分からないとフォルダも分からないので、全プロセスの分を数える）。対象アプリがすでに起動していたら注意を出す（アプリより先に記録を開始するのが確実） |
| 対象アプリのファイルへの他のプロセスのI/O | プロセス指定・併用のとき、対象アプリが中身を読み書きしたファイル（ページングI/Oでない読み書き・サイズの変更・フラッシュをしたもの。`FileKey`・ファイルオブジェクトで判定）へのOSの遅延書き込み・キャッシュ補充・ウイルス対策・検索インデックスのI/Oも残す（`matchesFile`）。開いただけ・ライブラリとして読み込んだだけのファイルや、一覧を取っただけのフォルダは、どのプログラムも使うもの（Windowsのライブラリ、フォント、ユーザーのフォルダなど）が多いので、ほかのプロセスのI/Oは残さない。ほかのプログラムが素材のフォルダに触れた分も見たいときは、そのフォルダを対象フォルダに指定する。アプリの要求の集計（Read・Write・レイテンシ）には入れず、ページングI/Oの量にだけ入れる。再生しない（`SkippedOtherProcess`） |
| フォルダの変更通知・メモリマップ | フォルダの変更を待つ要求（`DirectoryNotify`）と、ファイルのメモリへの割り当て・解除（`MapView` / `UnmapView`。開始前からの割り当ても）を残す。どちらも再生しない |
| プロセス | 開始時に動いていたプロセスと、記録中に始まった・終わったプロセスを、親・コマンドライン・終了コード付きで `processes.jsonl` に残す。対象プロセスは実行ファイルのパスとバージョンも残す。対象かどうか（子プロセスを含む）は、プロセスが起動したとき（開始時に動いていたものは開始時）に決めて、変えない。終わったプロセスも、同じプロセスIDで次のプロセスが起動するまで覚えておく（ファイルを閉じる処理やメモリの解除は、終了の知らせより後に届くため）。開始時に動いていたものは、親の起動時刻が子より後なら、親のプロセスIDが使い回されたものとして親子とみなさない。選んだアプリと同じフォルダのプログラムも対象にする（`options.programFolders`。プログラムのパスは、起動したときのコマンドライン、なければプロセスから読む） |
| 対象にしなかったプロセスのI/O | ファイル名は残さずに、プロセスとドライブ（共有）ごとの操作の件数と読み書きの量を数え、多い順に200件まで `session.json` の `otherProcessIo` に残す（件数の合計は `unrecordedEvents`） |
| ツールから起動したアプリ | 起動したアプリ（`options.launch`）とそのプロセスID（`launchedProcessId`）を `session.json` に残す。起動できなかったときは理由を注意事項に残し、記録は続ける |
| PCと保存先の環境 | 開始時に1回、CPUの型番・OSのバージョン・タイムゾーン、対象フォルダと記録の保存先のファイルシステムの種類・空き容量、ネットワークアダプター（種類・速度）、フィルタードライバーの一覧（`fltmc filters`）を `environment.json` に残す |
| ファイルの属性 | サイズ照会のついでに、属性（読み取り専用・スパース・圧縮・オフライン・クラウドのプレースホルダーなど）と作成・更新日時を残す |
| LucidLink | 任意のCLIを指定して `lucid perf --all --seconds 1` の標準出力・標準エラーを時刻付きで保存 |

サイズ照会はETWの非同期通知後に行うので、**Open時点・計測開始時点の厳密なサイズではありません**。観測値・照会時刻・Readから分かる初期サイズの下限・推定根拠を保存します。既存ファイルの初期伸長や切り詰めまで完全に忠実な再生が必要な場合は、別途スナップショットや同期フックが必要です。

ETWのCreateイベントにはDesiredAccessの全情報がないため、リプレイのOpenは、そのハンドルで記録された操作から必要なアクセス権を推定します（書き込み等があれば読み書き、読み取りがあれば読み取り、どちらも無ければ属性だけ）。属性だけの開き方は、ウイルス対策の開くときの検査の対象になりにくいので、元のアプリがデータ用に開いていた場合は、再生のほうが軽くなり得ます。取得できたShareAccessと一部のWriteThrough・Sequentialフラグを使用します。NoBuffering・LockFile・mmapの全参照・リンク・代替データストリーム等の完全再現は実装していません。フォルダの作成は1回の作成要求（`CreateDirectoryW`）で行い、親フォルダの存在確認を足しません。

記録で失敗した操作は、ダミーでも同じ形でストレージに届くものだけ、同じ要求として出し直します: 無い名前・無いパスの確認（`FILE_OPEN` でのOpen）、フォルダをファイルとして開く、ファイルの末尾より先の読み取り、フォルダの一覧の終わり、属性の問い合わせ。LucidLinkのようなストレージでは、失敗する確認もメタデータの往復になるためです。同じく失敗したか、失敗しなかったかは、再生結果に件数（`ReproducedFailures` / `FailuresNotReproduced`）と要求ごとの status で出し、結果を合わせる操作はしません。ロック・権限・容量不足など、ダミーに無い状態による失敗や、ダミーを書き換えてしまう失敗（作成・上書き・Write・Rename・Delete等）は出し直さず、`SkippedRecordedFailure` として数えます。記録で無い名前を確認しただけのパスにも、ダミー上のパスを割り当てます（何も作りません）。高速I/Oの拒否は、出し直されたIRPの方だけを再生します（`SkippedFastIoRetry`）。

開いた記録がないファイルオブジェクトへの要求（記録開始前に開かれていた、またはOSが開いた）は、その要求のためだけに開いて閉じます。元に無い Open・Close が増えるので、その回数を再生結果の `TemporaryOpens`（GUIでは「一時的に開いた回数」）に出します。

転送量は完了の実バイト数を優先し、完了不明の場合は要求サイズを使います。レイテンシは完了を対応付けられた成功Read/Writeのみ。P50/P95/P99は最大5%幅のヒストグラム上限値です。ユニークRead領域は観測された区間の和で、区間数が10万に達すると保守的な下限値になります。LucidLinkの必要キャッシュ容量やクラウド転送量をETWだけで確定するものではありません。

LucidLink統計はFilespace全体です。CLIのバージョン差を考慮して生テキストを保存し、キャッシュヒット率等を自動解釈した値として表示しません。LucidLinkの実マウントでのイベント対応・性能はその環境で確認してください。管理者のプロセスからユーザーの仮想ドライブが見えない場合、サイズ照会が失敗することがあります。対象フォルダとの照合は、ユーザー指定のパス、UNC、NTデバイスパス（CLIでは `--root-device` で指定可）のいずれかで行い、一致したパスはユーザー指定の表記（`L:\...`）に揃えて保存します。ETWに未解決のデバイスパスが残るファイルは再生対象から外し、その先頭部分（`\Device\...`）の上位20件を `session.json` の `unresolvedDevicePrefixes` に残します。このTraceEventが解釈しないFileIoイベントの種類と件数は `unhandledFileIoOpcodes` に残します。

記録は逐次保存し、保存待ちイベント数と未完了IRP数に上限を設けています。

**記録の保存と、途中で止まったとき**（ログのローテーションと書き込み前ログの一般的なやり方に合わせています）:

- イベントは番号付きのファイルに追記し、128 MiB（圧縮前）か10分で次のファイルに切り替えます。書き終えたファイルは、優先度を下げたスレッドでgzipに圧縮します（一時ファイル `.gz.tmp` に書いてディスクに書き込み、`.gz` に名前を変えてから元を消すので、どこで止まっても完全な方が残ります）。実測で約1/16になります（8,600万バイト → 540万バイト）。gzipは形式自体にCRC32を持つので、読むときに破損が分かります。
- 書き込み中のファイルは1秒ごとにOSへ渡し、10秒ごとにディスクまで書かせます。`session.json`（件数・欠落数など）も10秒ごとに書き直します。ツールが落ちても失うのは最後の約1秒、電源が落ちても約10秒です。
- 記録中のまま終わっている記録（ツールが落ちた、PCが止まった）は、アプリの起動時と記録を開いたときに「中断」（`Interrupted`）として確定します。最後の行が途中で切れていれば取り除き、件数・終了時刻を書き出されていた所までのデータから決めます。圧縮の途中で残ったファイルも片付けます。
- ツールが落ちると、ETWの計測セッションがOSの中に残り、バッファとCPUを使い続けます。次に記録を始めるときとアプリの起動時に、このツールのセッションでプロセスが無くなっているものを止めます。
- 記録の保存先の空き容量が5 GiBを下回ると警告し、1 GiBを下回ると記録を止めて保存します。
- 再生が途中で止まった（ツールやPCが止まった）ダミーを「初期状態に戻す」ときは、再生結果が欠けている可能性があるので、記録の書き込みすべての範囲を書き戻します。OSのETWイベント欠落・保存待ち行列の欠落・完了不明を品質情報に残します。リプレイ時の時刻順ソートは25,000件単位の外部ソートで、一度に全イベントをRAMへ読みません。ファイル一覧・1秒集計は記録規模に比例します。記録の停止後の集計は、記録を2回読むだけで済ませます（集計結果は `analysis.json` に保存し、記録を開くときはこれを再利用します）。

再生とベンチマークの実行では、記録された要求だけを試験先に発行します。パスの安全確認（データセットの外に出ないか、ジャンクションやリンクがないか）は、実行前に1回だけファイルシステムに問い合わせて行い、実行中は確認済みの結果をメモリ上で参照します。

## CLI

配布フォルダに `iorecorder-cli.exe` があります（GUIと同じ.NETのランタイムを使います）。以下はそのフォルダで実行する例です。

```powershell
# 管理者PowerShell: After Effectsと制作フォルダを30秒記録
.\iorecorder-cli.exe record --mode Hybrid --process AfterFX --root L:\Production --duration 30 --label "LucidLink cold"
# 管理者PowerShell: 記録を始めてからAfter Effectsを（ふだんの権限で）起動し、起動時の読み込みから記録する。Ctrl+Cで停止
.\iorecorder-cli.exe record --mode Process --launch "C:\Program Files\Adobe\Adobe After Effects 2025\Support Files\AfterFX.exe"

# 送る用のzipにまとめる（既定はデスクトップ） / 受け取ったzipを Recordings に展開する
.\iorecorder-cli.exe export --session <記録フォルダ>
.\iorecorder-cli.exe import --zip <記録のzip>

# 素材のフォルダだけでダミーを作る（省略時は、画面の「場所で絞り込む」で記録に保存した場所。--all-locations で全部）
.\iorecorder-cli.exe generate --session <記録フォルダ> --target L:\Bench\20261017-160000_replay --location L:\Production

# 通常権限: ダミー生成 → 初期アップロード・キャッシュ条件を準備 → 再生
.\iorecorder-cli.exe generate --session <記録フォルダ> --target L:\Bench\20261017-160000_replay
.\iorecorder-cli.exe replay --session <記録フォルダ> --target L:\Bench\20261017-160000_replay --workers 8   # 既定はThinkTime。記録の時刻どおりなら --timing Timeline

# 昇格後にドライブが見えない場合: 通常権限で解決してから、管理者側に渡す
.\iorecorder-cli.exe resolve-root --root L:\Production
.\iorecorder-cli.exe record --mode Folder --root L:\Production --root-device \Device\HarddiskVolume9\Production

# 集計を再作成 / 合成デモ / 実ETWの自動確認
# 実行済みのダミーを生成直後の状態に戻す（書き換わった部分だけ書き戻す）
.\iorecorder-cli.exe reset --target L:\Bench\20261017-160000_replay
# 再生中の試験先のI/Oも記録して（管理者）、元の記録と比べる
.\iorecorder-cli.exe replay --session <記録フォルダ> --target L:\Bench\20261017-160000_replay --record
.\iorecorder-cli.exe compare --session <記録フォルダ>
.\iorecorder-cli.exe analyze --session <記録フォルダ>
.\iorecorder-cli.exe demo
.\iorecorder-cli.exe verify-etw
```

プロセス名・PID・rootは複数回指定できます。`record`の時間を省略した場合はCtrl+Cで停止します。`--no-size-probe`でサイズ照会を、`--no-open-files`で開始時に開いているファイルの確認を無効にできます。`replay --process-only` / `--root-only`で収集時の分類に従って対象を切り出せます。`replay --paging UnmatchedReads|None|All`でページングI/Oの扱いを、`--trim-leading-idle`で先頭の空白の扱いを選べます。`--root-device`は`--root`と同じ数・同じ順に指定します。`--launch` はプログラムかショートカットを指定し（`--launch-args` で引数を変えられます）、そのアプリがもう起動していれば起動はせずに、名前で記録します。`--location` は `generate`・`compare`・`analyze` に複数回指定できます。

## 開発とテスト

無料の.NET 10 SDKでビルドします。`scripts\setup-dotnet.ps1`はMicrosoft公式のインストールスクリプトを用い、ユーザーフォルダにSDKを配置します。`scripts\build.ps1`でビルド・自動テスト・ランタイム同梱版の生成を行います。SDKを全ユーザー向けに入れる場合は `winget install Microsoft.DotNet.SDK.10` でも構いません。

GitHub Actionsでは、次のものが動きます（`.github/workflows`）。

- **CI**: `main` への変更とプルリクエストごとに、Windowsでビルドと自動テストを行います（GitHubの共有マシンでは、再生のタイミングのテストだけ許容幅を広げます）。
- **CodeQL**: C#のコードとワークフローを、セキュリティの観点で静的解析します（公開リポジトリのとき）。
- **Scorecard**: OpenSSF Scorecardで、リポジトリの運用（依存関係の固定、権限、ブランチの保護など）を評価します（公開リポジトリのとき）。
- **Release**: `v0.2.0` のようなタグを送ると、配布版をビルドしてzipとSHA-256を作り、ビルドの来歴の証明（公開リポジトリのとき）を付けて、GitHubのリリースに載せます。
- **Dependabot**: NuGetのパッケージ、.NET SDK、Actionsの更新を毎週提案します。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\setup-dotnet.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\build.ps1
# 個別に実行する場合
dotnet run --project tests\IoRecorder.Tests -c Release
# GUIスモークテスト: 配布版は管理者起動なので、通常権限で動く版をビルドして実行する
dotnet build src\IoRecorder.App -c Release -p:SmokeBuild=true
src\IoRecorder.App\bin\Release\net10.0-windows\IORecorder.exe --smoke-test artifacts\ui
```

テストはRead/Writeの合計、ユニーク領域、Lazy Manifest、サイズ変更、Allocation、Rename、delete-on-close、失敗操作、隔離、外部ソート、キャンセル等に加え、ページングI/Oの分離と再生方針、存在確認の失敗後の新規作成、ディレクトリ判定、Rename宛先の保留、root照合、外部ソート後の再生クロック開始を、合成イベントで検証します。ベンチマークについては、同じseed（数字・文字列）でI/O列が一致すること、比率とパターンの形、生成・実行・負荷ごとの集計とHTMLレポートまでを検証します。GUIスモークテストは合成データで画面遷移・検索・ダミー生成・再生を確認し、PNGを保存します。

実ETWの確認には **`Verify ETW.cmd`** を使います。UACを許可すると、専用の小さなファイルに対してRead/Write・伸長・切り詰め・Rename（パス指定と、開いたままのハンドル）・Delete・存在確認の後の新規作成・非バッファ書き込み後のキャッシュ付きRead・BACKUP_SEMANTICSでのディレクトリオープンを実行し、記録結果を検証します。`RESULT.txt` に項目ごとの判定を出します。PASS/FAILを決める項目（基本操作・root一致・欠落0・新規作成判定・ディレクトリ判定）と、このPCのETWの挙動を示す参考項目（INFO: Rename宛先・ページング分離・未解釈のイベント）があります。結果は `ドキュメント\IORecorder\Verification\日時_verify-etw` に残ります。実ETW・LucidLink・After Effectsの実機確認は、合成トレースによるテストとは別の工程です。
